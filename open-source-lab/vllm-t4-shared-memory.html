Case 002 · GPU kernel bugfix

修复 Tesla T4 上的 80 KiB 共享内存溢出

vLLM issue #36802 的首请求崩溃并不是显存不够，而是一个 Triton block 临时申请了超过 T4 硬件上限的共享内存。我把报错还原成可计算的 Q / K / V tile 账单，再用真实 2×T4 验证修复。

先用大白话说

GPU 里有一块很快但很小的“工作台”，叫 shared memory。这个 attention 内核一次把 Q、K、V 三组数据都摆上工作台，共要 80 KiB；Tesla T4 的工作台只有 64 KiB，所以还没开始算就被硬件拒绝。修复不是换模型，而是让 T4 每轮少搬一半 K / V token：同样的活分更多轮做，工作台占用降到约 48 KiB。

这类错误容易被误解成“GPU 显存不够”。但错误里的 shared memory 指每个 CUDA block 的片上临时空间，不是显卡的 16 GB 全局显存。加 CPU offload 可以帮助模型装入显存，却不能改变单个 block 的 64 KiB 上限。

先认识六个词

Triton

用 Python 风格代码编写 GPU kernel 的语言和编译器；这里负责生成 attention 内核。

Kernel

在 GPU 上并行执行的一段函数。launch 前，运行时会检查它需要的硬件资源。

Shared memory

同一个 thread block 共享的高速片上内存，容量远小于显存。

Tile

一次搬进工作台并处理的数据小块。tile 越大，循环可能越少，但临时空间更大。

SM75

Turing 架构的 compute capability 7.5；Tesla T4 属于这一代。

BF16 → FP32

T4 不原生支持 BF16，vLLM 把模型计算提升为 FP32；每个元素从 2 字节变成 4 字节。

报错是什么，怎样做到同条件复现？

上游 issue 报告在 T4 上运行 nvidia/Nemotron-Content-Safety-Reasoning-4B，第一个请求就失败：

triton.runtime.errors.OutOfResources:
out of resource: shared memory
Required: 81920, Hardware limit: 65536

原报告是 4×T4。Kaggle 只有 2×T4，因此我使用 tensor parallel 2、cpu_offload_gb=4，并关闭 hybrid KV cache manager，让 FP32 模型能够装入。它们只解决容量问题，不会改变 head size、元素宽度或单 block shared-memory 上限。

从模型加载到内核崩溃，原本发生了什么？

Before · the first request never reaches generation

模型声明 BF16Nemotron / Gemma 3
T4 自动提升BF16 → FP32
4 bytes / element
Unified Attentionhead_size = 256
K/V tile = 32Q + K + V = 80 KiB
Kernel launch 失败T4 limit = 64 KiB

Gemma 3 的优化策略为 Unified Attention 选择 32-token K / V tile。在 FP16 / BF16 下未必有问题，但 T4 上的实际执行 dtype 是 FP32，每个元素翻倍为 4 字节，于是同一块 tile 的临时空间也翻倍。

81,920 字节是可以一项项算出来的

  • Q tile：16 行 × 256 head size × 4 bytes = 16 KiB
  • K tile：256 head size × 32 tokens × 4 bytes = 32 KiB
  • V tile：32 tokens × 256 head size × 4 bytes = 32 KiB
  • 合计：16 + 32 + 32 = 80 KiB = 81,920 bytes

Q tileK tileV tile虚线：T4 64 KiB 上限

报错里的两个数字与这份账单完全吻合。这把“可能是 Triton 的问题”收敛成一个具体结论：SM75 + FP32 + head 256 + tile 32 的静态内核形状超过硬件限制。

一个很合理、但实际无效的尝试

Triton 的报错通常会建议降低 num_stages，因为流水线 stage 增多可能复制临时 buffer。于是我先验证了 num_stages=1。

结果：完整模型仍然请求 81,920 字节，数字一字不变。说明这 80 KiB 来自同时存活的 Q / K / V tile，而不是软件流水线的额外复制。

保留这个失败实验很重要：它排除了一个常见解释，也防止后续维护者再次走同一条路。真正有效的控制量必须是 K / V tile size。

修复：只在精确命中问题形状时把 tile 32 改成 16

我没有按模型名硬编码，也没有让所有 T4 都降级。策略只在三个条件同时成立时触发：

  1. 设备是 SM75；
  2. attention head size = 256；
  3. Query 和 KV 的元素宽度都是 4 bytes（FP32）。
if capability == 75 and head_size == 256
   and q_element_size == 4 and kv_element_size == 4:
    return 16  # K/V tile: 32 → 16

return existing_tile_policy(...)

tile 变小以后，同一段序列会通过更多轮循环处理，attention 公式、覆盖范围和输出 dtype 都不变。Q 仍是 16 KiB，K / V 各降到 16 KiB，总计约 48 KiB，低于 T4 的 64 KiB 上限。

主要风险是 T4 上更小的 tile 可能带来延迟或吞吐回退。当前证据已经证明它把“完全无法运行”变成“可以完成生成”，但合入前仍值得补充稳定的性能对比，看看能否在 16 与其它候选 tile 之间找到更好平衡。
